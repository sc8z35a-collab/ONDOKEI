# Battery Relay 設計

## 構成

- `MonitorService`: ユーザー可視のフォアグラウンドサービス。通常15秒、Turbo 5秒、保護時60秒で公開 API を読みます。deep sleep中の周期を維持するため、計測中だけ安全タイムアウト付き `PARTIAL_WAKE_LOCK` を管理します。
- `MeasurementRepository`: 計測、1分バケット保存、UI 通知を直列化します。Turboのライブ点はメモリで置換し、DB書き込みを最大1回/分に制限します。DB初期化はApplicationのI/O Executorで行います。
- `HistoryStore`: SQLite の1分バケット。通常は30分超を削除し、時計巻き戻しで未来扱いになった正常行を破壊せず、常に最大31行へ制限します。
- `MainActivity`: 上部の端末タブ、即時更新、Turbo切替、分単位変化率、2本の30分グラフを描画します。
- `ShareHost`: ローカル TCP サーバー、DNS-SD 公開、ペアリング、暗号化スナップショット応答を担当します。
- `NsdBrowser`: `_batteryrelay._tcp.` を検索します。Android 14以降は継続的なサービス情報コールバック、旧版は再試行付き直列名前解決を使います。解決待ち・遅延再試行・コールバック・確定peerを合算して最大32サービスです。
- `RemoteDeviceManager`: 最大8接続をApplicationスコープで所有し、表示切替やActivity再生成で切断しないよう管理します。
- `RemoteClient`: 選択中は通常15秒/Turbo 5秒、非選択またはUI非表示中は60秒で暗号化スナップショットを取得します。手動fresh要求は成功応答まで世代番号で保持します。

## データ保持

1. 通常15秒/Turbo 5秒で読み、`floorDiv(timestamp, 60000)` の1分バケットへ保存します。
2. 同じ分のライブ値はメモリで置換し、次の分へ移る際に前の分の最終値を永続化します。
3. 通常は `captured_at < now - 30min` をトランザクション内で削除します。
4. システム時計を巻き戻して既存の正常行が一時的に `captured_at > now` になっても、その理由だけでは削除しません。`readWindow` では現在時刻より後の行を表示・共有対象から除外し、時刻が追いつけば再び利用できます。
5. SQLite全体は、現在/過去の新しい行を優先しつつ最大31行に二次制限します。時計異常でも無制限に増えません。
6. 共有元は送信直前、共有先は復号直後にも30分窓を再適用します。
7. 共有先の履歴はメモリ上だけで、次回スナップショットに置換されます。

## 分単位変化率

**最新サンプルそのもの**が対象メトリックを持つことをまず確認し、その最新値と、30秒以上前にある直前の有効点から次式で計算します。

`rate = (newValue - oldValue) / ((newTime - oldTime) / 60000)`

固定60秒と仮定しないため、OS のスケジューリング遅延があっても `/分` の値が歪みにくい設計です。最新サンプルで温度を取得できなければ温度レートも `NaN` とし、「取得不可」の横に古い温度変化率を出しません。

## 共有プロトコル v1

### 発見

共有元は Android Network Service Discovery で TCP ポート、共有 ID、16バイト salt、P-256 公開鍵を広告します。共有データは DNS-SD TXT へ載せません。待受と共有先ソケットは検出したWi‑Fiの `Network` へ固定し、Wi‑Fi切替時はセッション鍵を保持したまま再バインド・再広告します。

探索側はサービス名単位で、旧APIの解決キュー、Android 14+の `ServiceInfoCallback`、失敗後の遅延retry、確定peerを一つの総量として扱い、最大32サービスに制限します。消失サービスのtombstoneは60秒TTL・最大64件、retry Runnableは名前ごとに1個で、発見・消失・停止時に明示キャンセルします。

### ペアリング

1. 共有先が一時 P-256 鍵ペアを生成します。
2. ECDH 共有秘密を計算し、共有 ID と画面上の128ビット共有キーを HKDF-SHA-256 のコンテキストへ含めて一時鍵を導出します。
3. 共有先は AES-256-GCM で認証されたペア要求を送ります。コードそのものは送りません。
4. 共有元は認証成功時だけ、ランダムなセッション ID と256ビットセッション鍵を暗号化応答します。

### スナップショット

各要求はセッション単位の単調増加 `seq` を持ち、要求／応答の AAD にも含めます。共有元は再利用または逆行した番号を拒否します。時刻同期には依存しません。

画面の「更新」から送る要求だけが暗号化済みの `fresh` フラグを含みます。共有先はfresh要求の世代番号を保持し、ネットワーク要求が成功するまで完了扱いにしません。通信中にさらに更新要求が来た場合も次の要求として残ります。

共有元はfresh要求時だけ応答直前にAndroid公開APIを再読込します。定期ポーリングは共有元の最新キャッシュを使うため、共有元端末へ二重の測定負荷を与えません。

受信側では、ホストの `generatedAt` と各サンプルの年齢差を使って受信端末の時計へ再基準化します。UIの鮮度はTCP応答受信時刻ではなく、再基準化された**最新実測サンプル時刻**を使います。`receivedAt` は通信診断用に別フィールドで保持します。

サーバーエラーはtransportエラーと分離します。`invalid_session`、version mismatch、stale share、viewer limitなどの永久エラーは明示的に終了し、rate limitは短い再試行、Socket/Wi‑Fi障害だけをネットワーク回復として扱います。

## 電力・熱ポリシー

| 状態 | 表示中のローカル測定 | 選択中の共有先 | 非選択/画面非表示の共有先 |
|---|---:|---:|---:|
| 通常 | 15秒 | 15秒 | 60秒 |
| Turbo | 5秒 | 5秒 | 60秒 |
| 省電力または熱状態「重度」以上 | 60秒 | 60秒 | 60秒 |

Turboは選択中のソースへ適用します。リモート端末を選択している間、ローカルサンプラーは通常15秒（または保護60秒）のままにし、ローカルタブへ戻るとTurbo 5秒へ復帰します。

`HandlerThread` のタイマーはdeep sleepだけでは正確に進まないため、Foreground Serviceの計測中は `PARTIAL_WAKE_LOCK` を保持します。1回の取得には10分のframework timeoutを設定し、正常動作中は5分ごとに更新します。明示停止時は即時解放します。この方式は周期精度と電池消費のトレードオフがあるため、省電力/高熱時は60秒へ退避します。

測定、共有待受、暗号処理、接続処理、DB初期化/停止flushはバックグラウンド側で実行します。通知とSQLiteの更新は最大1分に1回です。明示的な「計測を停止」では共有元・共有先の全セッションを破棄しますが、端末タブを切り替えるだけでは破棄しません。

### 防御上限

- 受信1メッセージ: 共有元8 KiB、共有先24 KiB、JSON深度8
- 接続タイムアウト: 5秒、共有元読み取りタイムアウト: 1.5秒
- 認証前同時接続: 全体8、送信元IPごと1（超過は即時拒否、待ち行列なし）
- TCP受付: 送信元IPまたはIPv6 /64ごとに1分120回まで
- ペアリング試行: 成否を問わず1 IP あたり1分に5回まで
- 認証済み取得: セッションごとに1分30回まで、即時測定は全体・セッションごとに最低5秒
- 同時閲覧セッション: 8
- セッション: 最終利用から2時間で失効
- 128ビット共有キー: 5分ごとに更新
- 探索中サービス: 解決待ち・retry・callback・peerを合算して32件まで
- 消失サービスtombstone: 60秒TTL、最大64件
- 取得失敗: 鍵を保持したまま最大60秒の指数バックオフと障害時DNS-SD再解決

## Android 互換性

- `minSdk 26`（Android 8.0）、`compileSdk/targetSdk 36`
- Android 13 以降では通知権限を要求します。
- Android 10 以降で OS thermal status を追加表示します。
- Android 14以降は継続更新型NSD APIでアドレス変更を追跡し、旧版は低頻度の再解決を継続します。
- Manifestには `WAKE_LOCK` を宣言します。
- Android 17 / targetSdk 37向けの `ACCESS_LOCAL_NETWORK` を先行宣言しています。現在target 36では従来互換動作で、target 37へ上げる際は実行時許可フローを追加する必要があります。

## 署名

配布版は長期保存した同一release鍵を必須とします。Gradleのreleaseビルドと `build-local.sh` は、release鍵が明示設定されていない状態で配布版を生成しません。開発用は別ファイル名 `BatteryRelay-1.3.1-dev.apk` とし、既存 `.dev-signing.jks` の従来alias `battery-relay` と互換を維持します。

## 非目標

- CPU/SoC 温度の推測や `/sys` のベンダー依存読み取り
- インターネット越しの共有
- クラウドアカウント、ユーザー追跡、恒久履歴
- 医療・安全機器としての利用
